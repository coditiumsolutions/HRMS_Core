# 5. Deployment

## Model
Manual, script-driven **single-server IIS deployment** (Windows Server) of a framework-dependent app. No containers, no CI/CD pipeline, no infrastructure-as-code.

## `scripts/deploy/DeployToIIS.bat` – what it does
1. `dotnet clean` (Release) → `dotnet restore` → `dotnet build -c Release`.
2. Stops IIS app pool **`HRMS`** and site **`HRMS`** (WebAdministration module) and kills any `HRMBT.Web.exe`.
3. Deletes everything in `C:\HRMSDeploy`, recreates it.
4. `dotnet publish -c Release -o C:\HRMSDeploy --self-contained false --runtime win-x64`.
5. Verifies `web.config` (generated by the Web SDK) and `HRMBT.Web.dll`.
6. Starts the app pool and site again.
7. Prints the public URL **`http://178.105.20.255:82/`** and a server checklist.

### Server prerequisites (from the script)
- IIS site `HRMS`, physical path `C:\HRMSDeploy`, HTTP binding on **port 82**, blank host name.
- App pool `HRMS`: **No Managed Code**, 64-bit.
- Firewall: inbound TCP 82.
- **ASP.NET Core 8 Hosting Bundle** installed (matches `net8.0`; the README's ".NET 9" is wrong).
- SQL Server reachable from the web server (connection string in `appsettings.json`, port 50001).

## Alternative: Visual Studio publish
`Properties/PublishProfiles/FolderProfile.pubxml` → file-system publish to `D:\Publish EBills\HRMS` (a developer machine path; folder name hints at reuse from another project).

## Local development
`dotnet run --project src/HRMBT.Web/HRMBT.Web.csproj` → `http://localhost:5128`, `ASPNETCORE_ENVIRONMENT=Development` (runtime Razor compilation, no HSTS/exception page redirect).

## Database deployment
No automatic migration at startup (`Database.Migrate()` is not called). Schema is applied by hand: EF migrations via CLI and/or the SQL scripts in `database-schema*.sql`, `scripts/`, `Migrations/*.sql`; several tables are assumed to pre-exist (see [03-data-structures.md](03-data-structures.md)). Backup/export helpers: `tools/export-db-schema.ps1`, `tools/export-database-production.ps1`.

## State that must survive a deploy
The script **wipes the whole deploy folder** each time, including `wwwroot/uploads/employees/` (employee documents) and any production-edited config. Uploaded files were therefore **destroyed on every deployment** – `EmployeeDocuments` rows then pointed to missing files. Fixed 2026-11-24: the script copies the uploads to `C:\HRMSBackups\uploads_<timestamp>` before the wipe and restores them after publishing; `EmployeeDocuments:StorageBasePath` (example in `appsettings.Production.example.json`) keeps them outside the deploy folder altogether. Missing files are flagged in the Attachments tab.

## Environments / configuration
- **Live topology (checked 2026-11-16):** `hr.coditium.com` resolves to a different host than the IP in `DeployToIIS.bat` (80/443 open, port 82 closed). SQL Server 2022 with database `HRBTK` is reachable on that host's port 1433; the `localhost,50001` / `HRMS` string in `appsettings.json` and `DefaultConnection4` do not match it, so production must override the connection string outside the committed file. The deploy script's printed URL (`http://178.105.20.255:82/`) is out of date.
- Single `appsettings.json` with multiple connection strings; `DefaultConnection` points at `localhost,50001` (the production server itself). No `appsettings.Production.json` (and `appsettings.Development.json` is git-ignored), no environment-specific transforms, no secret store.
- Logging: default console/debug providers only; no file/Serilog/Application Insights; IIS stdout log is the only trace.

## Deployment gaps
- No automated tests/build gate; no CI; no rollback (folder is deleted before publish; failure leaves site down).
- Downtime on every release (site stopped before build output is replaced).
- HTTP only; no TLS binding configured; no health-check endpoint.
- Hard-coded production IP/ports in the batch file; DB access uses the `sa` superuser account.
- `_build_verify/` build output is checked into git.
